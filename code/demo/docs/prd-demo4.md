# 시연 ④ PRD — 14건의 질문을 자동으로 채점

> 5주차 발표(2026-05-13) 시연 4건 중 마지막.
> 청중이 "AI 시스템의 품질을 정량 측정할 수 있다 + 자가 수정 + 의도된 거절을 카운트한다"를
> 한 클릭 채점으로 본다.
>
> **버전**: v0.1 (2026-05-12)
> **선행**: 시연 ①·②·③의 백엔드 동작

---

## 1. 목적

기존 `run_eval.py`는 콘솔 출력만 한다. 본 시연은 같은 14건을 **라이브 카운터 + 진행률 + 처리 로그**로 시각화해, 청중이 "AI 시스템도 측정 가능하다"를 직관적으로 받아들이도록 한다.

청중이 인지해야 할 핵심 3가지:
1. **정량 측정** — 14건 한 번에 돌려 직접 성공 / 자가 수정 / Fallback / 실패를 자동 분류
2. **자가 수정의 빈도** — 어떤 질문이 1회로 안 되고 2~3회 만에 되는지 보임
3. **의도된 거절** — 답이 안 나오는 케이스는 실패가 아니라 환각 방지 성공

---

## 2. 발표 스토리 (5분)

> 1. (진입) "이제 14건을 한 번에 채점하겠습니다. 시연 ③에서 본 흐름을 14번 반복하는 거예요."
> 2. (시작 버튼) "시작"
> 3. (라이브) 위 4개 카운터가 차오름. 처리 로그가 1건씩 추가됨.
>    - 1-1 ✓, 1-2 ✓, 1-3 ✓, 2-1 🔁 자가 수정, 2-2 ✓, ...
> 4. (완료) "최종 결과: 9건 직접 성공, 3건 자가 수정, 0 Fallback, 3건 실패 (그 중 1건은 환각 방지)"
> 5. (해석) "성공률 79%는 이번 스터디 시연 수준입니다. 더 중요한 건 실패 3건 중 1건이 의도된 거절이라는 점이에요."

---

## 3. 입력
- 사용자 조작: "시작" 버튼 한 번 (또는 "중지")
- 평가셋은 고정 (`llm/eval/golden_qna.json` 14건)

---

## 4. 단계 분해

| 단계 | 내용 | 화면 |
|:--:|---|---|
| 진입 | 14건 목록 미리보기 + 4개 카운터 (모두 0) + "시작" 버튼 | 상단 카운터 카드 4개, 중앙 진행률, 하단 14건 표 |
| 실행 | "시작" 클릭 → SSE 시작 → 한 건씩 case_start/case_done 이벤트 | 처리 중인 건은 진행률 마커 + 카운터 증가 애니메이션 |
| 완료 | 통계 + 난이도별 직접 성공률 | 상단 통계 박스 + 표의 모든 건 색상 라벨 |

각 건의 결과 분류 규칙 (`run_eval.py`와 동일):
- `status="success" AND attempt=1` → **직접 성공** (1회 성공)
- `status="success" AND attempt>1` → **자가 수정**
- `status="fallback_success"` → **Fallback**
- `status="failure"` → **완전 실패**

## 6. API 명세 (2개)

### 6.1 GET `/api/demo4/eval-set`

14건 메타 미리보기.

```json
{
  "total": 14,
  "cases": [
    { "id": "1-1", "difficulty": 1, "category": "단순", "question": "EMD_여수_상암동..." },
    { "id": "1-2", "difficulty": 1, "category": "단순", "question": "..." }
  ],
  "by_category": { "단순": 3, "중간": 6, "복잡": 5 }
}
```

### 6.2 GET `/api/demo4/run` (SSE)

평가 시작. 한 건씩 결과를 SSE 이벤트로 푸시.

이벤트 종류:
```
data: {"type": "started", "total": 14}

data: {"type": "case_start", "index": 0, "id": "1-1", "difficulty": 1, "category": "단순", "question": "..."}

data: {"type": "case_done", "index": 0, "id": "1-1", "category": "단순",
       "outcome": "first_try",  // first_try | retry | fallback | failure
       "attempts": 1,
       "summary": "1회 성공·1건"}

data: {"type": "finished", "stats": { "first_try": 9, "retry": 3, "fallback": 0, "failure": 2 },
       "by_difficulty": { "단순": [3,3], "중간": [4,6], "복잡": [2,5] }}
```

서버는 sequential로 한 건씩 `query_with_trail` 호출. Gemini 호출이 한 건당 ~2~5초이므로 전체 ~60~80초.

## 7. 백엔드 구현 메모

### 7.1 함수 재사용
- `text_to_typeql.query_with_trail` (시연 ③에서 추가) — 결과 분류에 필요한 trail 정보 있음
- `text_to_typeql.GOLDEN_SET` — 14건 메타 데이터 출처
- `chat.py`는 무수정

### 7.2 분류 로직
```python
def classify(trail_dict: dict) -> str:
    status = trail_dict["final_status"]
    if status == "fallback_success": return "fallback"
    if status == "failure": return "failure"
    # success
    last = trail_dict["trail"][-1]
    return "first_try" if last["attempt"] == 1 else "retry"
```

### 7.3 SSE 라우터
기존 `runner.py` 패턴 재사용 안 함 (그건 subprocess 스트림). 새로 `AsyncGenerator[dict]` 만들어 `_sse_from_async_gen` (server.py) 으로 직렬화.

## 9. 수용 기준
1. 14건 전부 처리 완료
2. 카운터 4개 합 = 14
3. SSE 이벤트가 한 건씩 도착 (한꺼번에 X)
4. 1-1·1-2·1-3 (단순) 3건 모두 직접 성공
5. 3-1~3-5 (복잡) 중 일부는 자가 수정·실패 정상 (반복 회차 결과의 약간 변동 허용)
6. 책임님 라이브 시연 1회 통과
