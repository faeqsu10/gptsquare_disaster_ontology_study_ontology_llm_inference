§ 2.2 fun 함수 5종 (functions.tql)

파일: study/wildfire-poc/db/functions.tql (146줄)

  • 정의: TypeDB 3.x에서 도입된 사용자 정의 함수. TypeQL 쿼리 안에서 호출 가능.
  • rule과의 차이: 3.x에서 rule이 폐기되고 fun으로 대체. rule은 백그라운드 자동 추론, fun은 명시적 호출 — 호출 위치·시점 추적이 명확.

5종 시그니처

#fun 이름시그니처줄번호역할
1sources_by_status_v2($status_filter: string) -> { source }22~26source를 availability-status로 필터
2grade_to_score($grade_in: string) -> { double }34~52risk-grade를 점수로 매핑
3alert_to_score($alert_in: string) -> { double }59~71alert-level을 점수로 매핑
4s_priority_to_state_v2 ⭐($sp_in: double, $version_in: string) -> { string }81~106s_priority + 정책 버전 → State 5단계. threshold-set 노드 동적 조회
5resolve_state_v2($base, $safety, $alert: string) -> { string }114~146State Override (hazard_gate 1순위, alert_경보 6순위)

설계 원칙 (functions.tql:3-13)

  1. 임계값·가중치 하드코딩 금지 — 그래프의 threshold-set·weight-set 노드 조회
  2. 매개변수와 attribute 매칭 분리 (REP1 회피) — has X $internal; $internal == $param;
  3. lookup·분기는 OR 절 + let 변수
  4. 기존 Python 추론(graph_inference.py)과 병존 — fun이 같은 결과 보장 (test_python_vs_fun.py로 검증)

예시 — grade_to_score 전체 코드 (functions.tql:34-52)

fun grade_to_score($grade_in: string) -> { double }: match { $grade_in == "정상"; let $score = 0.00; } or { $grade_in == "낮음"; let $score = 0.20; } or { $grade_in == "다소높음"; let $score = 0.55; } or { $grade_in == "높음"; let $score = 0.75; } or { $grade_in == "매우높음"; let $score = 1.00; }; return { $score };

TypeQL의 OR 절을 lookup 테이블로 사용. 입력 문자열에 대응하는 점수를 let $score = ...로 바인딩 후 반환. 원자료 산식 GRADE_SCORE 매핑을 그래프 안에 직접 구현.

§ 2.3 TypeDB 추론엔진의 4가지 추론 기법

docs/study/w04/TypeDB_추론엔진_이해/의 4가지 핵심 기법. fun이 이들을 지원하므로 그래프 안에서 복잡한 추론이 가능하다.

§ 2.3.1 선언적 추론 (Declarative Reasoning)

  • "어떻게 찾는지"가 아니라 "무엇이 참인지"만 적는다.
  • fun 본문은 절차문이 아닌 조건 명세. 실행 순서는 TypeDB 엔진이 결정.
  • 위 grade_to_score(§ 2.2)는 "정상이면 0.00"이라고 적을 뿐, 어느 조건을 먼저 검사할지 명시하지 않는다.
📎 참고: 절차적 표현이면 if grade == "정상": return 0.00; elif ... 식으로 평가 순서가 코드에 박힌다. 선언적 표현은 평가 순서를 엔진에 위임 — 최적화·병렬화 여지가 생긴다.

§ 2.3.2 재귀 호출 (Recursive Function)

  • 함수가 자기 자신을 호출하여 단계 수가 가변적인 탐색 수행.
  • 그래프 도달 가능성 분석에 유용 (예: 발화지점에서 N단계 인접 zone 모두 추적).
  • 본 시스템 functions.tql에는 재귀가 없으나, 산불 확산 시뮬레이션 같은 후속 기능에서 사용 예정.

예시 — w04 자료의 산불 확산 추론

fun all_reachable($from: forest-zone) -> { forest-zone }: match { (zone-a: $from, zone-b: $next) isa zone-adjacent-to-zone; } or { let $mid in all_reachable($from); # 자기 자신 호출 (zone-a: $mid, zone-b: $next) isa zone-adjacent-to-zone; }; return { $next };

발화지점 $from에서 직접 인접한 zone + 그 인접한 zone의 인접한 zone ... 까지 N단계 추적. 단계 수가 가변적이므로 재귀가 필수.

§ 2.3.3 중첩 호출 (Nested Function)

  • 함수 안에서 다른 함수를 호출하여 작은 블록을 조립.
  • 본 시스템에선 추론 계층(graph_inference_fun.py)이 grade_to_score, alert_to_score, s_priority_to_state_v2, resolve_state_v2를 순서대로 호출하는 형태.
  • 직접적인 fun 안의 fun 호출은 let $score in alert_to_score(...) 패턴으로 표현.

§ 2.3.4 부정 표현 (Negation)

  • "X가 없는 경우"를 조건으로 삼아 누락·예외를 검출.
  • 본 시스템에선 resolve_state_v2의 $safety_in != "작업 불가" 처럼 부등호로 부정을 표현 (functions.tql:122, 134).
  • 향후 "보고서가 없는 종료 사건" 같은 감사 기능 구현 시 not { ... } 블록으로 확장 예정.

§ 2.5 fun + 외부화 결합 — INSERT 한 줄로 정책 변경

s_priority_to_state_v2의 핵심 메커니즘 (functions.tql:81-106 전체):

fun s_priority_to_state_v2($sp_in: double, $version_in: string) -> { string }: match $t isa threshold-set, has config-version $cv, has th-low $lo, has th-mid-low $ml, has th-mid-high $mh, has th-high $hi; $cv == $version_in; # ← 동적 조회의 핵심 { $sp_in < $lo; let $state = "GeneralManagement"; } or { $sp_in >= $lo; $sp_in < $ml; let $state = "EnhancedMonitoring"; } or { $sp_in >= $ml; $sp_in < $mh; let $state = "ReviewPreWatering"; } or { $sp_in >= $mh; $sp_in < $hi; let $state = "PriorityPreWatering"; } or { $sp_in >= $hi; let $state = "ImmediatePreWatering"; }; return { $state };

동작 흐름

  1. fun 호출 시 두 인자 $sp_in, $version_in 전달 (예: 0.315, "v1")
  2. match 절에서 모든 threshold-set 노드를 후보로 가져옴
  3. $cv == $version_in 조건으로 정책 버전 필터 → v1 카드 1개만 남음
  4. 그 카드의 4개 임계값을 $lo, $ml, $mh, $hi로 바인딩
  5. OR 절로 입력 점수가 어느 구간에 속하는지 판정
  6. 해당 구간의 let $state = "..." 결과 반환

REP1 회피 패턴

# 안 됨 (TypeDB 3.x 제약): $t has config-version $version_in; # 됨 (functions.tql 채택): $t has config-version $cv; $cv == $version_in;

attribute 매칭과 매개변수 비교를 분리. functions.tql:6-8 주석에 명시.

정책 변경 시나리오 — INSERT 한 줄로 시뮬레이션

# v2 정책 카드 추가 (Python 코드 0줄 수정) insert $t isa threshold-set, has threshold-set-id "TS_S_PRIORITY_V2", has metric-name "S_priority_to_state", has config-version "v2", has th-low 0.15, has th-mid-low 0.30, has th-mid-high 0.50, has th-high 0.70; # 동일 점수 0.315에 대해 다른 결과 s_priority_to_state_v2(0.315, "v1") → "EnhancedMonitoring" s_priority_to_state_v2(0.315, "v2") → "ReviewPreWatering" ⬆️

fun 재작성 없이, 같은 함수가 정책 카드만 바꿔서 다른 결과를 산출.

§ 3.1 Python 추론 — graph_inference.py

§ 3.2 fun 추론 — graph_inference_fun.py

TypeQL 안에서 fun 5종을 순서대로 호출하여 그래프 내부에서 추론 수행.

§ 3.3 동일 결과 회귀 검증

  • 감사 추적 — 결과의 산출 시점·정책 버전·입력을 함께 저장 가능

§ 4.2 LLM #1 — Text-to-TypeQL 변환

§ 4.2.1 호출 파라미터 (text_to_typeql.py:31-35, 131-139)

GEMINI_MODEL = "gemini-2.5-flash" MAX_RETRIES = 3 _client = genai.Client(api_key=os.environ["GEMINI_API_KEY"]) response = _client.models.generate_content( model=GEMINI_MODEL, contents=prompt, config=types.GenerateContentConfig( system_instruction=SCHEMA_SUMMARY, temperature=0.0, ), )
  • temperature=0.0 → 결정론 보장 (같은 prompt에 같은 출력)
  • system_instruction=SCHEMA_SUMMARY → 스키마·문법·select 규칙을 항상 시스템 컨텍스트로 주입

§ 4.2.2 SCHEMA_SUMMARY 구성 (text_to_typeql.py:41-109)

LLM #1에 매 호출마다 주입되는 시스템 프롬프트, 약 70줄. 구성:

  1. entity 5종의 attribute 목록
  2. relation 정의
  3. state 6종 enum
  4. TypeQL 3.x 문법 핵심 (match, select, reduce, sort, limit, or)
  5. select 절 작성 규칙 — entity 변수만 select 금지, 필요 attribute 명시
  6. 질문 유형별 권장 select 패턴 — 7가지 (위험도/등급/MOCK source/임계값/가중치/시점/State별 정렬)
  7. 출력 규칙 — 코드 펜스 없이 순수 TypeQL만

§ 4.2.3 출력 후처리 — _strip_code_fence (text_to_typeql.py:112-119)

LLM이 종종 ```typeql ... ``` 형식으로 감싸므로 코드 펜스 제거 후 순수 쿼리만 추출.

§ 4.2.4 실행 함수 — _execute_typeql (text_to_typeql.py:142-150)

def _execute_typeql(typeql: str) -> tuple[bool, list | str]: try: with make_driver() as driver, driver.transaction(DB_NAME, TransactionType.READ) as tx: answer = tx.query(typeql).resolve() rows = list(answer.as_concept_rows()) serialized = [_serialize_row(row) for row in rows] return True, serialized except Exception as exc: return False, str(exc)
  • 성공 → (True, [serialized_rows])
  • 실패 → (False, "에러 메시지") — 예외 문자열을 그대로 반환

§ 4.3 Self-correcting 재시도 로직

파일: study/wildfire-poc/llm/text_to_typeql.py:173-237의 query_with_self_correction()

핵심 루프 (text_to_typeql.py:184-211)

for attempt in range(1, max_retries + 1): typeql = _generate_typeql(question, last_error) ok, output = _execute_typeql(typeql) if ok and len(output) > 0: return { "status": "success", "attempt": attempt, "typeql": typeql, "results": output, "fallback_used": False, } if not ok: last_error = f"실행 에러: {output}" else: last_error = "쿼리 성공했으나 결과 0건. 조건이 맞는지 확인하세요."

§ 4.3.1 성공 판정 기준 (2가지 동시 충족)

조건검사 위치의미
ok == Truetext_to_typeql.py:192TypeDB가 쿼리를 예외 없이 실행 (문법·스키마 OK)
len(output) > 0text_to_typeql.py:193결과 행이 1개 이상

정답 비교 없음. 의미적 정합성은 검증되지 않음.

§ 4.3.2 재시도 prompt에 에러 첨부 (text_to_typeql.py:127-129)

if last_error: prompt += f"\n\n⚠️ 직전 시도가 실패했습니다. 에러:\n{last_error}\n수정해서 다시 작성하세요."
  • 첫 시도: 사용자 질문만 prompt에 포함
  • 2~3차 시도: TypeDB가 던진 예외 또는 "결과 0건" 메시지가 prompt에 첨부됨
  • LLM이 에러 메시지를 보고 자체 수정 후 재생성

§ 4.3.3 4가지 결과 분기

§ 4.4 Fallback — golden_typeql 대체

위치: text_to_typeql.py:213-228

case = GOLDEN_SET.get(case_id) if case_id else None if case and "golden_typeql" in case: golden_q = case["golden_typeql"] ok, output = _execute_typeql(golden_q) if ok: return { "status": "fallback_success", "attempt": max_retries, "typeql": golden_q, "results": output, "fallback_used": True, "warning": "⚠️ Gemini가 쿼리 생성에 실패하여 사전 작성된 정답으로 대체했습니다.", }
  • golden_qna.json의 각 케이스에 사전 작성된 golden_typeql이 보관됨.
  • 3회 재시도 모두 실패해야만 발동.
  • 응답에 warning 필드 자동 부착 — 사용자가 "AI가 못 푼 케이스, 사전 정답 사용" 인지 가능.
  • case_id가 없으면 fallback 시도조차 안 함.

§ 4.6 환각 방지 메커니즘

구조적 사실: 별도의 "환각 차단 로직"이 존재하지 않는다. 환각 방지는 다음 두 정책의 부산물이다.

  1. 성공 판정에 len(output) > 0 포함 (text_to_typeql.py:193)
  2. LLM #2가 results 입력 없이 답변 생성하지 않음 (chat.py 구조)

시나리오 — "1990년 1월 광주 동구 위험도?" 처리 흐름

1. LLM #1: TypeQL 생성 match $r isa run-context, has reference-time $t; $t < 2021-01-01T00:00:00; select $r; 2. TypeDB 실행 ok = True, output = [] ← 결과 0건 3. 성공 판정 ok=True AND len(output)>0 → False last_error = "쿼리 성공했으나 결과 0건..." 4. 재시도 (2회): 동일하게 0건 5. Fallback (case_id=3-4, golden_typeql 실행) golden_typeql도 1990년 데이터 없음 → 0건 → fallback_success 조건(if ok:) 통과하나 results=[] 6. status="failure" 반환 7. LLM #2: results 입력 없음 → 정형 응답 생성 "해당 시점의 데이터가 존재하지 않습니다."

LLM #2가 "1990년 광주는 추정컨대..." 같은 환각 답변을 만들 가능성 자체가 차단됨. results가 없으므로 LLM에 컨텍스트가 없다.
